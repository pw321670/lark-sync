# Obsidian Feishu Core Sync Functionality

## Goal

实现 Obsidian 飞书同步插件的核心功能，包括 OAuth 授权、完整设置界面和后台同步功能，让用户可以通过 OneDrive 跨设备使用而无需重复授权。

## What I already know

* 当前项目已有插件框架（scaffold 阶段完成）
* 存在独立脚本 `auth.js` 和 `sync.js` 作为参考实现
* 插件已有基础设置界面和预览功能
- 用户要求三个核心功能：OAuth 跨设备同步、完整设置界面、快捷后台同步
- 希望通过 subagent 多智能体并行开发

## Assumptions (temporary)

* OAuth 授权信息需要通过 OneDrive 同步在设备间共享
* 后台同步需要非阻塞的异步处理机制
* 界面需要简洁清晰，符合 Obsidian 设计规范

## Decision (ADR-lite)

### 决策1: OAuth 跨设备同步机制

**Context**: 需要实现 OAuth 跨设备同步，让用户在一台设备授权后，在其他设备上无需重复授权

**Decision**: 采用配置文件同步方案
- 将 OAuth 授权信息存储在 Obsidian 插件数据目录中
- 依赖 OneDrive 同步整个保险库，授权信息自动跨设备可用
- 利用 Obsidian 现有的 `saveData()` API 进行数据持久化

**Consequences**:
- ✅ 实现简单，无需额外的加密存储机制
- ✅ 可靠性高，依赖成熟的 OneDrive 同步
- ✅ 与现有插件数据管理方式一致
- ⚠️ 依赖用户配置 OneDrive 同步（但这是目标用户群体的常见配置）
- ⚠️ 需要处理授权过期和刷新逻辑

### 决策2: 后台同步实现策略

**Context**: 需要实现不阻塞用户界面的后台同步功能，支持大型保险库的长时间同步

**Decision**: 采用 Web Worker 独立线程方案
- 使用 Web Worker 在独立线程中执行文件同步逻辑
- 通过 postMessage API 实现主线程与 Worker 之间的通信
- 在 Worker 中执行文件遍历、上传、状态管理等耗时操作

**Consequences**:
- ✅ 完全不阻塞主线程，用户体验最佳
- ✅ 支持大型保险库和长时间同步操作
- ✅ 符合现代插件开发的最佳实践
- ✅ 跨平台兼容性优秀（Windows/macOS/Linux）
- ⚠️ 实现复杂度中等，需要设计消息协议
- ⚠️ 需要处理 Worker 的错误传递和调试

**实现策略**: 渐进式实现
- 阶段1: 基础异步函数版本，确保功能正确性
- 阶段2: 迁移到 Web Worker，保持接口不变
- 阶段3: 优化错误处理和进度反馈机制

### 决策3: 同步按钮 UI 设计

**Context**: 需要为用户提供便捷的同步触发方式，同时保持界面整洁

**Decision**: 采用左侧边栏图标 + 可配置快捷键的组合方案
- 在 Obsidian 左侧边栏添加同步图标（Ribbon 图标）
- 图标显示当前同步状态（空闲/同步中/成功/失败）
- 支持在 Obsidian 快捷键设置中配置同步快捷键
- 点击图标或按快捷键都可以触发同步

**Consequences**:
- ✅ 符合 Obsidian 插件的设计规范和用户体验习惯
- ✅ 显眼易用，同时支持鼠标和键盘操作
- ✅ 图标状态变化提供直观的视觉反馈
- ✅ 可配置快捷键满足高级用户的个性化需求
- ⚠️ 需要设计清晰的状态图标（使用 Emoji 或 SVG 图标）

**实现细节**:
- 使用 Obsidian 的 `addRibbonIcon()` API 添加左侧边栏图标
- 使用 `addCommand()` API 创建可配置快捷键的命令
- 图标状态：🔄 (同步中) ✅ (成功) ❌ (失败) ☁️ (空闲)

## Requirements (evolving)

### 功能需求

#### 1. OAuth 授权管理

- **完整认证流程**
  - 支持飞书 OAuth 2.0 授权码模式
  - 在 Obsidian 内置浏览器中完成授权（或调用系统浏览器）
  - 自动处理授权回调并获取 access_token 和 refresh_token

- **跨设备同步**
  - 授权信息存储在插件数据中，随 OneDrive 同步
  - 新设备自动检测已有授权，无需重复授权
  - 授权过期时自动刷新 token

- **授权状态管理**
  - 实时显示授权状态（未授权/已授权/过期）
  - 提供"重新授权"和"清除授权"功能
  - Token 刷新失败时提示用户重新授权

#### 2. 完整设置界面

- **核心功能配置**
  - 飞书应用 ID 和密钥配置
  - 根目录 token 配置
  - 文件排除规则配置（支持通配符和正则表达式）
  - 文件大小限制配置
  - 同步策略配置（手动/自动/定时）

- **界面设计要求**
  - 整洁清晰，符合 Obsidian Material Design 规范
  - 提供配置验证功能（检查连接性、权限等）
  - 支持导入/导出配置
  - 提供恢复默认配置功能

#### 3. 快捷后台同步

- **同步触发方式**
  - 在界面左側边栏提供显眼的同步按钮
  - 支持命令面板触发同步
  - 支持快捷键触发同步（可自定义）

- **后台同步机制**
  - 使用 Web Worker 在独立线程中执行同步
  - 同步过程中显示实时进度（当前文件、上传速度、剩余时间）
  - 支持暂停/恢复/取消同步操作

- **同步完成通知**
  - 成功：显示同步摘要（上传文件数、跳过文件数、耗时）
  - 失败：显示详细错误信息和恢复建议
  - 部分失败：列出成功和失败的文件清单

  - 清晰的接口定义和依赖管理

#### 模块间通信协议

```typescript
// 主线程 → Worker 消息类型
type WorkerCommand =
  | { type: 'start-sync'; config: SyncConfig }
  | { type: 'pause-sync' }
  | { type: 'resume-sync' }
  | { type: 'cancel-sync' }
  | { type: 'check-status' };

// Worker → 主线程消息类型
type WorkerMessage =
  | { type: 'sync-progress'; data: ProgressData }
  | { type: 'sync-complete'; result: SyncResult }
  | { type: 'sync-error'; error: ErrorInfo }
  | { type: 'sync-status'; status: SyncStatus };
```

## Research Notes

### PRD 组织结构分析

**方案 A: 单一 PRD + 模块化实现**
- 一个总 PRD 包含所有功能需求
- 通过技术模块划分来指导多智能体分工
- 适合功能关联紧密、依赖关系复杂的场景

**方案 B: 主 PRD + 子 PRD 结构**
- 一个总 PRD 定义整体架构和接口
- 多个子 PRD 分别对应独立功能模块
- 适合功能模块相对独立、可并行开发的场景

### 多智能体并行开发策略

基于功能模块的独立性分析：
- OAuth 授权模块：相对独立，可单独开发
- 设置界面模块：依赖 OAuth 接口，可并行开发
- 同步引擎模块：核心功能，依赖其他模块

### 推荐方案

**推荐方案 A**: 单一 PRD + 模块化实现
* 原因：
  - 三个功能模块之间有较强的依赖关系
  - 需要统一的用户体验和接口设计
  - 便于整体架构的一致性
* 多智能体分工：按技术模块和开发阶段分工
